Brief about the idea

SHROFF · Track 03

Millions of Indian MSMEs (kirana stores, small traders, tiny manufacturers) are new-to-credit: they run on cash and UPI and never kept formal books. Banks judge them on audited statements, ITR and a CIBIL score they simply don't have, so viable businesses are auto-rejected. Meanwhile, some borrowers who look clean on paper are quietly failing, and get through.

The idea: tell the truth in both directions

  • Approve the invisible-but-healthy. Read the business's real, consented digital money-trail (GST returns, UPI/bank flows via Account Aggregator, EPFO headcount) and score what the bureau can't see.
  • Catch the looks-fine-but-failing. Compare GST-declared turnover against bank-verified inflows on the same ₹ axis; flag bounce streaks, sliding receipts, distressed buyers.
  • Catch the phoenix. A spotless new company whose promoter's network reaches a struck-off / wilful-defaulter shell → deterministic REFER, regardless of score.

What the bank receives

  • A 300–900 Financial Health Score with four sub-scores: cash-flow · growth · stability · compliance.
  • Signed reason codes (TreeSHAP): every point on the score has an auditable reason. No LLM ever computes a number.
  • A verdict, APPROVE REFER DECLINE, with amount & tenure, emitted as an OCEN 4.0-aligned loan offer with risk-based pricing.

Why "Shroff"? The traditional Indian banker who judged merchants by cash-flow and conduct, never paperwork. This is that instinct, rebuilt from alternate data.

Opportunities & USP

How it differs · how it solves

How is it different from existing ideas?

  • Two-sided decisioning. Most inclusion tools only widen approval. SHROFF also tightens it: the same data catches clean-on-paper decliners, so the book gets healthier, not just larger.
  • Deterministic core, generative shell. Monotonic-constrained LightGBM + TreeSHAP. Any LLM use is env-gated narrative only, regulator-defensible by construction.
  • A third signal nobody scores: the entity graph. PAN-spine graph walk over real registries detects phoenix fraud: the promoter's network, not just the applicant.
  • Real registry data in the PoC. ~45,000 genuine government rows (MahaGST, SEBI/NSE, CBDT, MCA, RBI, OpenSanctions), not mocked.

How it solves the Track 03 problem

  • High NTC/NTB rejection → scores the consented alternate-data trail the statement can't show.
  • No unified framework → one health card: score + sub-scores + screening + EWS + offer.
  • Slow onboarding → near-real-time API (<100 ms/score), AA-consent native, ULI/OCEN adapter-ready.

USP in one line

"Sees the invisible borrower, in both directions: approves the invisible-but-healthy, catches the looks-fine-but-failing, and refers the phoenix the score alone would have lent to."

List of features offered by the solution

All working in the MVP today

1 · Scoring & explainability

  • 300–900 health score from ~45 engineered signals; 4 sub-scores (cash-flow · growth · stability · compliance) via monotonic LightGBM ensemble.
  • Calibrated 12-month PD (isotonic) behind every score.
  • Signed TreeSHAP reason codes: auditable, per-applicant.
  • What-if simulator: how the score moves if inputs change.
  • Early-warning strip: bounces, headcount drops, GST late/nil streaks.

2 · Screening & fraud graph

  • Negative-registry screening over ~45,000 real government rows: exact-ID hits (PAN/GSTIN/CIN/DIN) force the verdict; name-only hits stay advisory (bank AML pattern).
  • PAN-spine entity graph: walks promoters, co-directors, shared addresses; phoenix detection auto-REFERs.
  • GST-vs-bank divergence view: declared vs verified turnover, same ₹ axis.

3 · Lending rail & console

  • OCEN 4.0-aligned loan offer: risk-based pricing (Band A 13.77% → C 18.14%), reducing-balance EMI, tenure, validity.
  • AA consent artefacts (ReBIT v2 shape): consented, not scraped.
  • Underwriter console: portfolio ledger, health card, verdict stamp, entity graph.
  • Fixture fallback: console degrades gracefully if the API is down; a chip shows LIVE vs FIXTURE.

Architecture principles

  • No LLM on the decision path: generative is env-gated narrative only; nothing generative computes a number.
  • Overlays only worsen: screening/graph can downgrade a verdict, never rescue one.
  • Deterministic + reproducible: seed-42 pipeline, artifacts trained offline, loaded at boot, <100 ms/score.
  • Swappable data seam: SQLite in the PoC; the adapter layer makes AA-live / Postgres a config change.

Honesty box: what these numbers do and don't claim

  • Training set is synthetic (8,000 MSMEs encoding known risk economics). The numbers prove the pipeline (feature engine, monotone constraints, calibration, decisioning), not production performance.
  • In production the same pipeline retrains and recalibrates on the bank's own portfolio outcomes (sandbox phase).
  • Full reproducible proof page ships in-repo: docs/pipeline-proof.html; metrics in ml/artifacts/. Cold rebuild reproduces AUC/KS exactly.
  • All 3 personas verified through the live deployed API: input → score → verdict → OCEN offer.

Improvements — Phase 2

Refined prototype · developed since shortlisting

From 3 personas to any real business

  • Live GSTIN/PAN lookup: score any real identifier, not just the 3 demo personas — deterministically simulated financials, seeded from the identifier itself, so the same input always reproduces the same score.
  • Live document upload/download: download a sample business_profile.csv + monthly_history.csv, edit the numbers, upload them back — the score reflects exactly what's in the file, not a re-simulation.
  • Registry + entity-graph checks still run on the real ~45,000-row government dataset regardless of path — a flagged real GSTIN still force-declines even on edited financials.

Model transparency & lending depth

  • New Model & Score tab: the exact scorecard formula, band table, per-sub-model validation metrics, and monotone-constraint counts, read live from the trained bundle — never hardcoded.
  • Population-rank percentile on every score: "healthier than X% of N reference MSMEs," computed from the same trained model.
  • Second loan type: DSCR-based Term Loan sizing alongside the existing Nayak-norm Working Capital line.
  • Bank operational-impact overlay: quantifies onboarding + field-verification cost saved when an application auto-clears, with cited industry benchmarks, honestly zeroed whenever a human reviewer is still needed.

Console restructured into a real dashboard

Persistent navigation shell (Portfolio · Live demo) replaces a single scrolling page; the health card itself is now tabbed — Overview · Model & Score · Cash flow / GST · Screening & Graph · Supply chain / Rail — so a reviewer finds any one signal in one click instead of scrolling the whole file.
